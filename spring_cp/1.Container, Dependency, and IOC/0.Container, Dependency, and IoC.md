# Section 1-1 — Container, Dependency, and IoC

Let's build the concepts from the ground up:

```text
Object
  ↓
Dependency
  ↓
Dependency Injection
  ↓
IoC
  ↓
IoC Container
  ↓
Spring Container
  ↓
Spring Bean
```



# 1. What is an Object?

First, remember normal Java programming.

```java
class UserService {

    public void createUser() {
        System.out.println("Create user");
    }
}
```

We create an object:

```java
UserService service = new UserService();
```

The relationship is:

```text
UserService class
       ↓
    new UserService()
       ↓
UserService object
```

Normally, **you control object creation**.

```java
UserService service = new UserService();
```

This becomes important when objects start depending on other objects.



# 2. What is a Dependency?

Suppose we have:

```java
class EmailService {

    public void sendEmail() {
        System.out.println("Sending email");
    }
}
```

And:

```java
class UserService {

    private EmailService emailService;

    public UserService() {
        emailService = new EmailService();
    }

    public void register() {
        // register user

        emailService.sendEmail();
    }
}
```

`UserService` needs `EmailService`.

Therefore:

> **EmailService is a dependency of UserService.**

We can draw it as:

```text
UserService
     |
     | depends on
     ↓
EmailService
```

This is the meaning of **dependency**.



# 3. The problem with directly creating dependencies

The previous code works:

```java
class UserService {

    private EmailService emailService;

    public UserService() {
        emailService = new EmailService();
    }
}
```

But there is a design problem.

`UserService` is now tightly coupled to:

```java
EmailService
```

Imagine later we want SMS:

```java
class SmsService {

    public void sendSms() {
    }
}
```

Or:

```java
class WechatService {

    public void sendMessage() {
    }
}
```

Now `UserService` needs to know which implementation to create.

```java
class UserService {

    public UserService() {

        // tightly coupled
        emailService = new EmailService();

    }
}
```

The business class is responsible for **both**:

1. Business logic
2. Creating dependencies

That's undesirable.



# 4. Dependency Inversion

A better design is to depend on an interface.

```java
interface NotificationService {

    void send();
}
```

Implementations:

```java
class EmailService implements NotificationService {

    @Override
    public void send() {
        System.out.println("Email");
    }
}
```

```java
class SmsService implements NotificationService {

    @Override
    public void send() {
        System.out.println("SMS");
    }
}
```

Now:

```java
class UserService {

    private NotificationService notificationService;

    public UserService(
            NotificationService notificationService) {

        this.notificationService = notificationService;
    }

    public void register() {

        notificationService.send();
    }
}
```

Notice something important.

`UserService` no longer says:

```java
new EmailService()
```

Instead, somebody gives it a `NotificationService`.



# 5. Dependency Injection

This is where **Dependency Injection (DI)** comes in.

Instead of:

```java
class UserService {

    private NotificationService service;

    public UserService() {
        service = new EmailService();
    }
}
```

we do:

```java
class UserService {

    private NotificationService service;

    public UserService(
            NotificationService service) {

        this.service = service;
    }
}
```

And outside:

```java
NotificationService notification =
        new EmailService();

UserService userService =
        new UserService(notification);
```

The dependency is **injected** into `UserService`.

```text
             new EmailService()
                    |
                    ↓
           NotificationService
                    |
                    ↓
             UserService
```

So:

> **Dependency Injection means supplying an object's dependencies from outside rather than having the object create them itself.**



# 6. What is IoC?

Now we arrive at the exam's most important term:

## IoC = Inversion of Control

Normally:

```text
Your application
      |
      | creates
      ↓
    Objects
```

For example:

```java
UserService service = new UserService();
```

**You control object creation.**

With IoC:

```text
Spring Container
       |
       | creates
       ↓
     Objects
       |
       | injects
       ↓
Your application
```

Control has moved from your application to the framework.

That's why it's called:

> **Inversion of Control**

The control over object creation and wiring is **inverted**.



# 7. IoC vs DI

These two terms are related but not exactly identical.

### IoC

A general design principle:

> The framework/container controls things that your application would otherwise control.

### DI

One important technique for implementing IoC:

> Dependencies are supplied to an object instead of the object creating them.

Think:

```text
IoC
 |
 +-- Dependency Injection
 |
 +-- other forms of control inversion
```

For Spring, **IoC is primarily achieved through Dependency Injection.**



# 8. What is an IoC Container?

An **IoC Container** is a system that:

* creates objects
* manages objects
* connects objects
* provides objects to other objects
* manages their lifecycle

Conceptually:

```text
             IoC Container

        +---------------------+
        |                     |
        |   UserService       |
        |        ↓            |
        |   EmailService      |
        |        ↓            |
        |   UserRepository    |
        |                     |
        +---------------------+
```

Instead of you writing:

```java
UserRepository repository =
        new UserRepository();

EmailService email =
        new EmailService();

UserService user =
        new UserService(repository, email);
```

the container does this work.



# 9. Spring Container

Spring provides an IoC Container.

The most important interface is:

```java
ApplicationContext
```

For example:

```java
ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);
```

Conceptually:

```text
ApplicationContext
       |
       +---- UserService
       |
       +---- EmailService
       |
       +---- UserRepository
       |
       +---- OrderService
```

These managed objects are called:

# Spring Beans



# 10. What is a Spring Bean?

A **Bean** is simply an object that is created and managed by the Spring IoC container.

For example:

```java
@Component
public class UserService {

}
```

Spring sees `@Component` and can create a bean:

```text
Spring Container

      |
      ↓

new UserService()

      |
      ↓

UserService Bean
```

This is a very important distinction:

```text
Java Object
    ↓
Any object created with new

Spring Bean
    ↓
Object managed by Spring
```

Therefore:

> **Every Spring Bean is a Java object, but not every Java object is a Spring Bean.**



# 11. How does Spring know what to create?

There are several ways.

One common way is annotations.

```java
@Component
public class UserService {
}
```

```java
@Repository
public class UserRepository {
}
```

```java
@Service
public class OrderService {
}
```

Spring scans your classes and discovers these components.

Conceptually:

```text
@Component
@Service
@Repository
       |
       ↓
Component Scan
       |
       ↓
Spring Container
       |
       ↓
Create Beans
```



# 12. Dependency Injection with Spring

Now let's put everything together.

Repository:

```java
@Repository
public class UserRepository {

    public void save() {
        System.out.println("Save user");
    }
}
```

Service:

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }

    public void register() {
        repository.save();
    }
}
```

Spring creates:

```text
Spring Container

      |
      |
      +----------------+
      |                |
      ↓                ↓
UserRepository    UserService
                       |
                       |
                       +---- UserRepository
```

Spring performs approximately:

```java
UserRepository repository =
        new UserRepository();

UserService service =
        new UserService(repository);
```

You don't have to write those `new` statements yourself.



# 13. Constructor Injection

The example above uses:

```java
public UserService(UserRepository repository) {
    this.repository = repository;
}
```

This is called:

> **Constructor Injection**

It is generally the preferred form of dependency injection in Spring.

Why?

Because the object cannot be created without its required dependency.

```text
UserService
    |
    +-- requires UserRepository
```

The dependency is explicit.



# 14. Three common types of Dependency Injection

Spring supports three common forms.

## ① Constructor Injection

```java
public UserService(UserRepository repository) {
    this.repository = repository;
}
```

**Recommended.**



## ② Setter Injection

```java
public void setRepository(
        UserRepository repository) {

    this.repository = repository;
}
```

Useful when a dependency is optional or can be changed.



## ③ Field Injection

```java
@Autowired
private UserRepository repository;
```

Very simple, but generally less preferred for new code because dependencies are less explicit and testing/design can be weaker.

For interviews, remember:

```text
Constructor > Setter > Field
```

as the usual design preference.



# 15. A complete example

Let's create a small Spring application.

### Repository

```java
@Repository
public class UserRepository {

    public String findUser() {
        return "Mike";
    }
}
```

### Service

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }

    public void printUser() {

        String user =
            repository.findUser();

        System.out.println(user);
    }
}
```

### Controller

```java
@RestController
public class UserController {

    private final UserService service;

    public UserController(UserService service) {
        this.service = service;
    }

    @GetMapping("/user")
    public String user() {
        return service.getUser();
    }
}
```

The dependency graph is:

```text
UserController
       |
       ↓
UserService
       |
       ↓
UserRepository
```

Spring manages the entire graph.



# 16. What happens when the application starts?

Conceptually:

```text
Spring Boot starts
       |
       ↓
Create ApplicationContext
       |
       ↓
Scan components
       |
       ↓
Find @Repository
@Service
@RestController
       |
       ↓
Create Beans
       |
       ↓
Resolve dependencies
       |
       ↓
Inject dependencies
       |
       ↓
Application ready
```

For example:

```text
UserRepository
      ↓
UserService
      ↓
UserController
```

Spring must create the dependencies in a usable order.



# 17. The most important mental model

When learning Spring, don't think:

> "`@Autowired` magically creates an object."

Instead think:

```text
              Spring Container

                     |
          manages object graph
                     |
       +-------------+-------------+
       |                           |
       ↓                           ↓
UserRepository              UserService
                                   |
                                   |
                            injected dependency
                                   |
                                   ↓
                           UserRepository
```

Spring is essentially managing an **object graph**.

For a larger application:

```text
Controller
    |
    ↓
Service
    |
    +--------→ Repository
    |
    +--------→ PaymentService
    |
    +--------→ EmailService
```

Spring constructs and wires this graph.



# 18. Why is this useful?

Imagine testing `UserService`.

Without DI:

```java
class UserService {

    UserRepository repository =
        new UserRepository();

}
```

It's difficult to replace the repository.

With DI:

```java
class UserService {

    private final UserRepository repository;

    UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

You can provide a fake implementation:

```java
UserRepository fakeRepository =
    new FakeUserRepository();

UserService service =
    new UserService(fakeRepository);
```

This makes code:

* loosely coupled
* easier to test
* easier to change
* easier to maintain



# 19. A real-world analogy

Think about a restaurant.

Without IoC:

```text
Chef

  |
  +-- goes to market
  +-- buys vegetables
  +-- buys meat
  +-- hires waiter
  +-- prepares kitchen
  +-- cooks
```

The chef is responsible for everything.

With IoC:

```text
Restaurant Management
        |
        +-- provides ingredients
        +-- provides kitchen
        +-- provides waiter
        |
        ↓
      Chef
        |
        ↓
    Cooking
```

The chef focuses on **cooking**, while the container handles the surrounding infrastructure.

This is essentially the Spring philosophy:

> **Your application focuses on business logic; Spring manages infrastructure and object wiring.**

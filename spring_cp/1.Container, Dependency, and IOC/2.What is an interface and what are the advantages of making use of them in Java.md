# Dependency Injection — Exam Topic

This is one of the **most important Spring interview/exam concepts**. The key is to understand the problem first, then DI as the solution.

---

## 1. What is a dependency?

A **dependency** is an object that another object needs to perform its job.

For example:

```java
class UserService {

    private EmailService emailService;

    public UserService() {
        emailService = new EmailService();
    }

    public void register() {
        // register user
        emailService.sendEmail();
    }
}
```

`UserService` needs `EmailService`.

Therefore:

```text
UserService
     |
     | depends on
     ↓
EmailService
```

`EmailService` is a **dependency** of `UserService`.

---

# 2. What is Dependency Injection?

**Dependency Injection (DI)** means:

> An object's dependencies are provided to it from the outside instead of the object creating those dependencies itself.

Compare these two approaches.

### Without DI

```java
class UserService {

    private EmailService emailService;

    public UserService() {
        emailService = new EmailService();
    }
}
```

`UserService` creates its own dependency:

```text
UserService
    |
    | creates
    ↓
EmailService
```

### With DI

```java
class UserService {

    private EmailService emailService;

    public UserService(EmailService emailService) {
        this.emailService = emailService;
    }
}
```

Now somebody outside provides the dependency:

```java
EmailService email = new EmailService();

UserService user =
    new UserService(email);
```

The relationship becomes:

```text
Outside code
     |
     | provides
     ↓
EmailService
     |
     ↓
UserService
```

That is **Dependency Injection**.

---

# 3. Why is it called "Injection"?

Because the dependency is effectively **injected into** the object.

```java
UserService service =
    new UserService(emailService);
                         ↑
                    dependency
                    injected here
```

The `UserService` doesn't need to know:

```java
new EmailService()
```

It simply receives an `EmailService`.

---

# 4. The most important principle

Remember this contrast:

```text
Without DI:

Class → creates → Dependency


With DI:

External system → provides → Dependency → Class
```

Or even more simply:

> **Don't create your dependencies; receive them.**

---

# 5. DI with interfaces

DI becomes especially powerful when combined with **interfaces**.

Suppose:

```java
interface NotificationService {

    void send();
}
```

Two implementations:

```java
class EmailNotification
        implements NotificationService {

    public void send() {
        System.out.println("Email");
    }
}
```

```java
class SmsNotification
        implements NotificationService {

    public void send() {
        System.out.println("SMS");
    }
}
```

Then:

```java
class UserService {

    private final NotificationService notification;

    public UserService(
            NotificationService notification) {

        this.notification = notification;
    }
}
```

`UserService` doesn't care whether the implementation is:

```text
EmailNotification
       OR
SmsNotification
       OR
PushNotification
```

It only knows:

```text
NotificationService
```

This creates **loose coupling**.

---

# 6. Advantages of Dependency Injection

There are several important advantages.

## Advantage 1 — Loose coupling

This is probably the **most important advantage**.

Without DI:

```java
class UserService {

    private EmailService email =
        new EmailService();
}
```

`UserService` is tightly coupled to `EmailService`.

With DI:

```java
class UserService {

    private final NotificationService notification;

    UserService(NotificationService notification) {
        this.notification = notification;
    }
}
```

Now:

```text
UserService
     |
     ↓
NotificationService
     ↑
     |
 ------------------------
 |          |           |
Email      SMS        Push
```

You can change the implementation without modifying `UserService`.

---

# 7. Advantage 2 — Easier testing

This is extremely important in real-world development.

Suppose your real repository connects to a database:

```java
class UserRepository {

    public User findUser() {
        // access database
    }
}
```

Your service:

```java
class UserService {

    private final UserRepository repository;

    UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

During testing, you can provide a fake repository:

```java
class FakeUserRepository
        extends UserRepository {

    public User findUser() {
        return new User("Test User");
    }
}
```

Then:

```java
UserRepository fake =
    new FakeUserRepository();

UserService service =
    new UserService(fake);
```

You don't need a real database.

So:

```text
Production

UserService
     ↓
RealDatabaseRepository


Test

UserService
     ↓
FakeRepository
```

This makes **unit testing much easier**.

---

# 8. Advantage 3 — Easier to change implementations

Imagine your application starts with:

```text
PaymentService
     ↓
PayPal
```

Later you want:

```text
PaymentService
     ↓
Stripe
```

With DI:

```java
interface PaymentService {
    void pay();
}
```

You can switch implementations:

```java
new PaypalPaymentService()
```

to:

```java
new StripePaymentService()
```

without changing the business logic.

With Spring, the container can perform this wiring for you.

---

# 9. Advantage 4 — Better separation of responsibilities

Without DI:

```text
UserService

 ├── business logic
 ├── create database object
 ├── create email object
 ├── configure email
 └── manage dependencies
```

Too many responsibilities.

With DI:

```text
Spring Container
 ├── creates objects
 └── wires dependencies

UserService
 └── business logic
```

This follows the idea of **separation of concerns**.

The service focuses on its job.

---

# 10. Advantage 5 — Centralized object management

In a Spring application, the container manages dependencies:

```text
                 Spring Container

                       |
        +--------------+--------------+
        |              |              |
        ↓              ↓              ↓
   UserService    OrderService   PaymentService
        |              |
        ↓              ↓
   Repository     Repository
```

Instead of every class manually constructing its dependencies, Spring manages the object graph.

---

# 11. Advantage 6 — Better maintainability

Imagine a large application:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

And:

```text
OrderService
    ↓
PaymentService
    ↓
NotificationService
```

If every class uses `new` everywhere, changing one component can require modifications throughout the application.

With DI, dependencies are explicit and externally controlled.

This makes large systems easier to maintain.

# 12. DI and Spring

Now connect this to Spring.

You write:

```java
@Repository
class UserRepository {
}
```

and:

```java
@Service
class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

Spring sees:

```text
@Repository
UserRepository
       ↓
Spring Container
       ↓
creates UserRepository bean


@Service
UserService
       ↓
Spring Container
       ↓
creates UserService bean
       ↓
injects UserRepository
```

Conceptually, Spring does something equivalent to:

```java
UserRepository repository =
    new UserRepository();

UserService service =
    new UserService(repository);
```

You don't manually perform the wiring.

That's where **IoC** comes into the picture.

---

# 13. DI vs IoC

This is a common exam question.

### Dependency Injection

A **technique**:

> Give an object its dependencies from outside.

### Inversion of Control

A broader **principle**:

> Control over object creation and management is transferred from application code to a framework/container.

Relationship:

```text
             IoC
              |
              ↓
       Dependency Injection
              |
              ↓
    Dependencies provided
       from outside
```

Spring primarily implements IoC through DI.

---

# 14. Three common types of DI

You should also know these.

### 1. Constructor Injection

```java
class UserService {

    private final UserRepository repository;

    UserService(UserRepository repository) {
        this.repository = repository;
    }
}
```

**Generally preferred in Spring.**

---

### 2. Setter Injection

```java
class UserService {

    private UserRepository repository;

    public void setRepository(
            UserRepository repository) {

        this.repository = repository;
    }
}
```

Useful when the dependency is optional or configurable after construction.

---

### 3. Field Injection

```java
class UserService {

    @Autowired
    private UserRepository repository;
}
```

Simple, but generally less preferred than constructor injection.

---

# 15. Why is constructor injection preferred?

Consider:

```java
class UserService {

    private final UserRepository repository;

    public UserService(
            UserRepository repository) {

        this.repository = repository;
    }
}
```

Advantages:

* Dependency is explicit
* Object cannot exist without required dependency
* `final` can be used
* Easier unit testing
* No reflection needed just to set the field
* Helps enforce a valid object state

For an exam, remember:

> **Constructor injection makes required dependencies explicit and ensures they are available when the object is created.**

# 16. A simple real-world analogy

Imagine a chef.

Without DI:

```text
Chef

 ├── build oven
 ├── buy ingredients
 ├── make plates
 ├── hire waiter
 └── cook food
```

The chef has too many responsibilities.

With DI:

```text
Restaurant

 ├── provides oven
 ├── provides ingredients
 ├── provides plates
 └── provides waiter

          ↓

        Chef
          |
          ↓
       Cook food
```

The chef receives what they need and focuses on cooking.

Similarly:

```text
Spring Container

 ├── creates Repository
 ├── creates Service
 └── injects dependencies

          ↓

       Service
          |
          ↓
    Business Logic
```

# 17. Exam-ready answer

If the exam asks:

> **What is dependency injection and what are the advantages of using it?**

A strong answer would be:

> **Dependency Injection is a design pattern in which an object's dependencies are provided to it from an external source instead of the object creating them itself. In Spring, the IoC container creates and manages beans and injects their dependencies.**
>
> **The main advantages are loose coupling, easier unit testing, easier replacement of implementations, better separation of concerns, centralized object management, and improved maintainability.**

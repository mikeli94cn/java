# How do you configure Spring Profiles? What are possible use cases where they might be useful?

This topic is about **Spring Profiles**, which allow you to configure different behaviors for different environments.

The key idea:

> **Spring Profiles provide a way to register different Beans and configuration values depending on the active environment, such as development, testing, and production.**

In short:

```text
Profile

    ↓

Choose environment

    ↓

Load corresponding Beans/configuration
```

Typical examples:

```text
dev
test
prod
```

---

# 1. Why do we need Profiles?

A real application usually has multiple environments:

```text
Developer machine
        |
        ↓
Testing environment
        |
        ↓
Production environment
```

But each environment has different settings.

Example: Database.

## Development

```text
Database:
    localhost

Username:
    dev_user
```

---

## Production

```text
Database:
    production-server

Username:
    prod_user
```

You do not want to modify code every time you deploy.

Spring Profiles solve this problem.

---

# 2. What is a Spring Profile?

A profile is a named configuration group.

Example:

```text
dev

test

prod
```

Spring can activate one or more profiles:

```text
Active profiles:

dev
```

Then Spring loads:

```text
dev configuration
```

---

# 3. Configuring Profiles with `@Profile`

The `@Profile` annotation controls whether a Bean is created.

Example:

```java
@Configuration
public class DatabaseConfig {


    @Bean
    @Profile("dev")
    public DataSource devDataSource() {

        return new H2DataSource();
    }


    @Bean
    @Profile("prod")
    public DataSource prodDataSource() {

        return new MySQLDataSource();
    }

}
```

Behavior:

## If profile is:

```text
dev
```

Spring creates:

```text
H2DataSource
```

---

## If profile is:

```text
prod
```

Spring creates:

```text
MySQLDataSource
```

---

# 4. How to activate a Profile?

There are several ways.

---

# Method 1: `application.properties`

Spring Boot:

```properties
spring.profiles.active=dev
```

Now:

```text
Active profile:

dev
```

---

# Method 2: Command line

When starting:

```bash
java -jar app.jar \
--spring.profiles.active=prod
```

This overrides the configuration file.

---

# Method 3: Environment variable

Linux:

```bash
export SPRING_PROFILES_ACTIVE=prod
```

Then:

```bash
java -jar app.jar
```

Spring reads:

```text
prod
```

---

# Method 4: Java system property

```bash
java \
-Dspring.profiles.active=test \
-jar app.jar
```

---

# 7. Common use cases of Profiles

## Use case 1: Different databases

Very common.

Development:

```text
H2 database
```

Production:

```text
MySQL/PostgreSQL
```

Example:

```java
@Configuration
public class DatabaseConfig {


    @Bean
    @Profile("dev")
    DataSource h2() {

        return new H2DataSource();
    }


    @Bean
    @Profile("prod")
    DataSource mysql() {

        return new MysqlDataSource();
    }

}
```

---

# Use case 2: Different logging configuration

Development:

```text
DEBUG logging
```

Production:

```text
INFO/WARN logging
```

Example:

```properties
# application-dev.properties

logging.level.root=DEBUG
```

```properties
# application-prod.properties

logging.level.root=INFO
```

---

# Use case 3: Mock services for testing

Example:

Production:

```java
@Service
@Profile("prod")
public class PaymentService {

    // real payment API
}
```

Testing:

```java
@Service
@Profile("test")
public class MockPaymentService {

    // fake payment
}
```

During tests:

```text
No real payment happens
```

---

# Use case 4: Different external services



```java
}
```

```java
@Service
```

# 10. Profile expressions

You can use expressions.

## NOT

Example:

```java
@Profile("!prod")
@Bean
public DebugService debugService(){

}
```

Means:

```text
Create Bean unless prod profile is active
```

---

## OR

Example:

```java
@Profile({"dev", "test"})
@Bean
public MockService mockService(){

}
```

Means:

```text
dev OR test
```

# 12. How does Spring implement Profiles internally?

The process:

```text
ApplicationContext startup

        |
        ↓

Read active profiles

        |
        ↓

Scan configuration

        |
        ↓

Check @Profile conditions

        |
        ↓

Register matching Beans only

        |
        ↓

Create Beans
```

Example:

```java
@Profile("prod")
@Bean
DataSource datasource()
```

If:

```text
active profile = dev
```

then:

```text
BeanDefinition not registered
```

# 13. Profiles and dependency injection

Example:

Interface:

```java
public interface PaymentService {

}
```

Production:

```java
@Service
@Profile("prod")
class RealPaymentService
        implements PaymentService {

}
```

Testing:

```java
@Service
@Profile("test")
class FakePaymentService
        implements PaymentService {

}
```

Then:

```java
@Autowired
PaymentService service;
```

Spring injects the correct implementation.

# 14. Profiles vs `@Qualifier`

They solve different problems.

## `@Qualifier`

Chooses among existing Beans:

```text
Multiple Beans exist

        ↓

Choose one
```

Example:

```java
@Qualifier("mysql")
```

---

## `@Profile`

Controls whether a Bean exists:

```text
Profile active?

        ↓

Create Bean or not
```

Example:

```java
@Profile("prod")
```

---

Comparison:

|         | `@Profile`           | `@Qualifier`         |
| ------- | -------------------- | -------------------- |
| Purpose | Enable/disable Beans | Choose Bean          |
| Time    | Application startup  | Dependency injection |
| Example | dev/prod             | mysql/oracle         |

# 17. Exam-ready answer

Question:

> **How do you configure profiles? What are possible use cases where they might be useful?**

A strong answer:

> **Spring Profiles provide a way to define different configurations and Beans for different environments. Profiles can be activated using `spring.profiles.active`, command-line arguments, environment variables, or system properties. Beans can be associated with profiles using the `@Profile` annotation, and Spring only creates those Beans when the corresponding profile is active. Common use cases include using different databases for development and production, enabling mock services during testing, changing logging configuration, and managing environment-specific application settings.**

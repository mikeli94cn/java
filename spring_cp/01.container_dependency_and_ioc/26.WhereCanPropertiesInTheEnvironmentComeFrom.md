# Where can properties in the Spring `Environment` come from?

This topic is about **Spring's Property Sources** and **how Spring resolves configuration values**.

The key idea:

> **Properties in Spring's `Environment` can come from many different sources. Spring collects them into a unified `Environment`, and when the same property exists in multiple places, higher-priority sources override lower-priority ones.**

Conceptually:

```text
                 Property Sources
                       |
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
 application.yml   Environment    Command line
                    variables
        ↓              ↓              ↓
        └──────────────┼──────────────┘
                       ↓
                 Spring Environment
                       ↓
             @Value / @ConfigurationProperties
```

---

# 1. What is a Property Source?

A **PropertySource** is simply a place where Spring can read configuration values.

Example:

```properties
server.port=8080
```

The property:

```text
server.port
```

has a value:

```text
8080
```

But where did it come from?

It could come from:

```text
application.properties
environment variable
command line argument
system property
database
custom file
```

Spring abstracts all these as:

```text
PropertySource
```

---

# 2. Common property sources in Spring Framework

Spring Framework itself supports several property sources.

## 1. Java system properties

These come from:

```bash
java -Dname=value
```

Example:

```bash
java -Dapp.name=OrderSystem -jar app.jar
```

Spring can read:

```text
app.name=OrderSystem
```

through:

```java
environment.getProperty("app.name")
```

---

## 2. Operating system environment variables

Example Linux:

```bash
export APP_NAME=OrderSystem
```

Spring can access environment variables.

For example:

```java
environment.getProperty("APP_NAME")
```

returns:

```text
OrderSystem
```

In Spring Boot, relaxed binding also allows:

```properties
app.name
```

to map to:

```text
APP_NAME
```

---

## 3. Property files

The most common source.

Example:

`application.properties`

```properties
app.name=OrderSystem
server.port=8080
```

Spring loads these values into the Environment.

---

## 4. YAML files

Spring Boot supports:

`application.yml`

```yaml
app:
  name: OrderSystem

server:
  port: 8080
```

Equivalent to:

```properties
app.name=OrderSystem
server.port=8080
```

---

## 5. Command-line arguments

Example:

```bash
java -jar app.jar --server.port=9090
```

Spring reads:

```properties
server.port=9090
```

Command-line properties usually have high priority because they are often used to override deployment settings.

---

# 3. Spring Boot adds many more property sources

Spring Boot greatly extends Spring's configuration mechanism.

The major Spring Boot property sources include:

---

# 1. Default properties

You can define:

```java
@SpringBootApplication
public class Application {

}
```

with:

```properties
spring.application.name=OrderService
```

---

# 2. `application.properties`

Typical location:

```
src/main/resources/application.properties
```

Example:

```properties
server.port=8080
spring.datasource.url=jdbc:mysql://localhost/db
```

---

# 3. Profile-specific properties

Example:

```
application-dev.properties

application-test.properties

application-prod.properties
```

Example:

`application-dev.properties`

```properties
database.url=jdbc:h2:mem:test
```

`application-prod.properties`

```properties
database.url=jdbc:mysql://production/db
```

Activated by:

```properties
spring.profiles.active=prod
```

Spring loads:

```text
application.properties

+

application-prod.properties
```

---

# 4. Environment variables

Very common in production.

Example:

Linux:

```bash
export SPRING_DATASOURCE_URL=jdbc:mysql://prod/db
```

Spring Boot maps it to:

```properties
spring.datasource.url
```

because:

```text
_  → .
uppercase → lowercase
```

Example:

```
SPRING_DATASOURCE_USERNAME
```

becomes:

```
spring.datasource.username
```

This is very common in:

* Docker
* Kubernetes
* Cloud deployments

---

# 5. Command-line properties

Example:

```bash
java -jar application.jar \
--server.port=9000
```

Overrides:

```properties
server.port=8080
```

---

# 6. External configuration files

Spring Boot also searches outside the application.

Example:

```
/config/application.properties
```

or:

```
./application.properties
```

This allows deployment-specific configuration without rebuilding the application.

---

# 7. Test properties

Spring tests can provide properties.

Example:

```java
@SpringBootTest(
    properties = {
        "app.name=TestApplication"
    }
)
class MyTest {

}
```

The test property overrides normal configuration.

---

# 8. `@TestPropertySource`

Example:

```java
@SpringBootTest
@TestPropertySource(
    properties = {
        "app.mode=test"
    }
)
class UserTest {

}
```

Useful for integration tests.

---

# 9. `@PropertySource`

You can add custom property files.

Example:

```java
@Configuration
@PropertySource("classpath:database.properties")
public class DatabaseConfig {

}
```

File:

```
database.properties
```

contains:

```properties
database.url=localhost
```

Spring adds it into the Environment.

---

# 4. Property precedence (important for exams)

When the same property exists in multiple sources:

Example:

`application.properties`

```properties
server.port=8080
```

Environment variable:

```bash
SERVER_PORT=9000
```

Command line:

```bash
--server.port=10000
```

Which value wins?

Spring uses **property source precedence**.

Higher priority overrides lower priority.

A simplified order:

```text
Higher priority
        ↑

Command-line arguments

Environment variables

Profile-specific files

application.properties

Default properties

        ↓
Lower priority
```

So:

```text
application.properties
        |
        | server.port=8080
        ↓
environment variable
        |
        | server.port=9000
        ↓
command line
        |
        | server.port=10000
```

Final value:

```text
server.port=10000
```

---

# 5. Why does Spring have so many sources?

Because applications run in many environments.

Example:

## Developer machine

```text
application-dev.properties

database=h2
logging=debug
```

---

## CI/CD testing

```text
environment variables

database=test-db
```

---

## Production

```text
Kubernetes secrets

database=production-db
password=******
```

The same application artifact can run everywhere:

```text
                 Same JAR
                    |
        ┌───────────┼───────────┐
        ↓           ↓           ↓
       dev         test        prod
```

Only configuration changes.

---

# 6. Example: same application, different environments

Java code:

```java
@Service
public class UserService {

    private final String databaseUrl;

    public UserService(
        @Value("${database.url}")
        String databaseUrl) {

        this.databaseUrl = databaseUrl;
    }
}
```

Development:

`application-dev.properties`

```properties
database.url=jdbc:h2:mem:test
```

Production:

`application-prod.properties`

```properties
database.url=jdbc:mysql://prod/db
```

No Java code changes.

Only:

```properties
spring.profiles.active=dev
```

or:

```properties
spring.profiles.active=prod
```

changes.

---

# 7. How this connects to `Environment`

Remember:

```java
@Autowired
Environment environment;
```

Then:

```java
String url =
    environment.getProperty("database.url");
```

Spring searches:

```text
Command line?
       |
Environment variable?
       |
application-prod.properties?
       |
application.properties?
       |
Custom PropertySource?
       |
Return value
```

# 9. Interview / exam answer

Question:

> **Where can properties in the Environment come from?**

A good answer:

> **Properties in Spring's Environment come from a collection of PropertySources. These can include property files such as application.properties and application.yml, profile-specific configuration files, system properties, environment variables, command-line arguments, and custom property sources added through mechanisms such as @PropertySource. Spring Boot adds additional configuration sources and defines an order of precedence, allowing higher-priority sources such as command-line arguments and environment variables to override lower-priority configuration files.**

---

# Short version to memorize

```text
Spring Environment
        |
        ↓
Properties come from:

✓ application.properties
✓ application.yml
✓ profile files
  application-dev.properties
✓ environment variables
✓ JVM system properties
✓ command-line arguments
✓ @PropertySource files
✓ test properties
✓ external configuration files

Spring Boot:
    adds more sources
    defines precedence rules
```

The important interview concept is:

> **`Environment` is not a single configuration file. It is a unified view over many property sources, with a defined priority order.**

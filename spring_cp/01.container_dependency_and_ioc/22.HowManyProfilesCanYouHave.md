## How many Spring Profiles can you have?

In **Spring Framework**, there is **no fixed limit** on how many profiles you can define.

You can have as many profiles as your application needs:

```text
dev
test
staging
prod
docker
aws
local
integration-test
...
```

For example:

```properties
spring.profiles.active=dev
```

You could define:

```text
dev
test
staging
prod
```

or a more detailed setup:

```text
local
dev
test
qa
staging
prod
aws
azure
docker
kubernetes
```

The number is essentially limited by practical considerations such as configuration complexity, not by a small predefined Spring limit.

---

## 1. You can activate multiple profiles at the same time

This is an important point.

You are **not limited to one active profile**.

For example:

```properties
spring.profiles.active=dev,aws
```

Now both `dev` and `aws` are active:

```text
Application
     │
     ├── dev
     │
     └── aws
```

A bean can require one of them:

```java
@Bean
@Profile("dev")
public PaymentService paymentService() {
    return new MockPaymentService();
}
```

Another bean can require `aws`:

```java
@Bean
@Profile("aws")
public StorageService storageService() {
    return new S3StorageService();
}
```

With:

```properties
spring.profiles.active=dev,aws
```

both beans can be created.

---

## 2. One bean can require multiple profiles

You can also write:

```java
@Bean
@Profile({"dev", "test"})
public PaymentService paymentService() {
    return new MockPaymentService();
}
```

This means the bean is active if **either `dev` OR `test`** is active.

Conceptually:

```text
@Profile({"dev", "test"})

        dev ───────┐
                   ├──> Bean enabled
       test ───────┘
```

So:

```text
active = dev       → enabled
active = test      → enabled
active = dev,test  → enabled
active = prod      → disabled
```

---

## 3. You can use profile expressions

Spring also supports profile expressions.

For example:

```java
@Profile("!prod")
```

means:

> Enable this bean when `prod` is NOT active.

You can also express more complex conditions, such as:

```java
@Profile("dev & !prod")
```

Meaning:

```text
dev is active
AND
prod is not active
```

So profiles aren't simply a fixed list of mutually exclusive environments.

## 4. Profiles are usually used for environments

A common application might have:

```text
local
dev
test
staging
prod
```

For example:

```text
                    Spring Application
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
            local         test         prod
              │            │            │
           H2 DB        Test DB      PostgreSQL
           Mock API     Mock API      Real API
           Debug        Test logs     Production logs
```

You might have:

### `application-dev.properties`

```properties
server.port=8080
spring.datasource.url=jdbc:h2:mem:devdb
```

### `application-prod.properties`

```properties
server.port=8080
spring.datasource.url=jdbc:postgresql://prod-db/myapp
```

Then:

```bash
java -jar app.jar --spring.profiles.active=dev
```

or:

```bash
java -jar app.jar --spring.profiles.active=prod
```

# 5. Profiles don't have to mean environments

This is a subtle but useful point.

You could use profiles for different **deployment/configuration dimensions**, although you should avoid creating too many unnecessarily.

For example:

```text
Environment:
    dev
    prod

Cloud:
    aws
    azure

Database:
    mysql
    postgres
```

You could theoretically activate:

```properties
spring.profiles.active=prod,aws,postgres
```

Then different beans/configurations respond to different profiles.

However, if the combinations become complicated:

```text
dev + aws + mysql
dev + aws + postgres
dev + azure + mysql
dev + azure + postgres
prod + aws + mysql
...
```

you can quickly create a **configuration explosion**.

So in real applications, profiles should generally represent meaningful configuration/environment choices rather than every possible combination.

# 6. How this relates to `@Profile`

Remember the relationship:

```text
@Profile
   ↓
Profile condition
   ↓
Should this BeanDefinition be registered?
   ↓
Yes
   ↓
Spring creates Bean
   ↓
DI
```

For example:

```java
@Service
@Profile("dev")
public class MockEmailService implements EmailService {
}
```

and:

```java
@Service
@Profile("prod")
public class RealEmailService implements EmailService {
}
```

With:

```properties
spring.profiles.active=dev
```

Spring effectively has:

```text
MockEmailService  → registered
RealEmailService  → not registered
```

With:

```properties
spring.profiles.active=prod
```

the situation reverses.

## 7. Important distinction: profiles vs `@Qualifier`

These two concepts are easy to confuse.

### `@Profile`

Answers:

> **Should this bean exist?**

```java
@Profile("dev")
@Component
class MockPaymentService {}
```

### `@Qualifier`

Answers:

> **Which existing bean should I inject?**

```java
public OrderService(
    @Qualifier("paypal") PaymentService paymentService) {
}
```

So:

```text
@Profile
   ↓
Bean existence

@Qualifier
   ↓
Bean selection
```

## Exam-ready answer

> **Spring does not impose a fixed number of profiles. An application can define as many profiles as needed, such as `dev`, `test`, `staging`, and `prod`. Multiple profiles can be active simultaneously, and `@Profile` can conditionally register beans based on the active profiles.**

### Short version to memorize

```text
How many profiles?
        ↓
No fixed limit
        ↓
Can define many profiles
        ↓
Can activate multiple profiles
        ↓
@Profile controls conditional Bean registration
```

A useful next concept is **how Spring decides which `application-{profile}.properties` files are loaded and which configuration wins when multiple profiles are active**.

# Why are you not allowed to annotate a `final` class with `@Configuration`?

This topic is about **how Spring implements `@Configuration` classes internally**.

The key idea:

> **A Spring `@Configuration` class cannot be `final` because Spring creates a CGLIB proxy subclass of the configuration class to manage `@Bean` methods and maintain Bean singleton behavior. A `final` class cannot be subclassed, so Spring cannot create the proxy.**

In short:

```text
@Configuration

        ↓

Spring creates CGLIB subclass proxy

        ↓

Requires inheritance

        ↓

final class cannot be extended

        ↓

Not allowed
```

---

# 1. What is `@Configuration`?

`@Configuration` tells Spring:

> "This class contains Bean definitions."

Example:

```java
@Configuration
public class AppConfig {

    @Bean
    public UserService userService() {
        return new UserService();
    }

}
```

Spring reads:

```text
AppConfig
    |
    +-- userService()
```

and registers:

```text
UserService Bean
```

---

# 2. Why does Spring need to proxy a `@Configuration` class?

Consider this configuration:

```java
@Configuration
public class AppConfig {


    @Bean
    public UserRepository userRepository() {

        return new UserRepository();
    }


    @Bean
    public UserService userService() {

        return new UserService(userRepository());
    }

}
```

At first glance, it looks like:

```java
userService()
        |
        ↓
new UserRepository()
```

creates a new repository every time.

But Spring promises:

> By default, Beans are singleton.

So Spring must ensure:

```text
id="4be2a5"
Only one UserRepository object exists
```

How?

By replacing:

```text
AppConfig
```

with:

```text
AppConfig$$SpringCGLIB$$Proxy
```

---

# 3. What does the CGLIB proxy do?

Original class:

```java
@Configuration
public class AppConfig {


    @Bean
    public UserRepository userRepository() {

        return new UserRepository();
    }

}
```

Spring creates something conceptually like:

```java
public class AppConfigProxy
        extends AppConfig {


    private UserRepository repository;


    @Override
    public UserRepository userRepository() {

        if(repository == null) {

            repository = super.userRepository();

        }

        return repository;
    }

}
```

The proxy intercepts calls.

Instead of:

```java
new UserRepository()
```

every time:

```text
id="b4tq6f"
Call userRepository()

        ↓

Proxy checks cache

        ↓

Return existing Bean
```

---

# 4. Why does this require inheritance?

CGLIB works by creating a subclass.

Example:

Original:

```java
public class AppConfig {

}
```

Generated:

```java
public class AppConfigProxy
        extends AppConfig {

}
```

This is normal Java inheritance.

But:

```java
final class AppConfig {

}
```

means:

```text
No class can extend AppConfig
```

Therefore:

```text
id="7tr9r3"
AppConfigProxy extends AppConfig

        X

Impossible
```

Spring cannot create the proxy.

# 5. Example of invalid code

This will fail:

```java
@Configuration
public final class AppConfig {


    @Bean
    public UserService userService() {

        return new UserService();
    }

}
```

Spring tries:

```text
Create proxy

        ↓

class AppConfig$$SpringCGLIB
        extends AppConfig

        ↓

Compiler/runtime error

```

because:

```java
final class
```

cannot be inherited.

# 6. Why can `@Component` be final but not `@Configuration`?

Good interview comparison.

## `@Component`

Example:

```java
@Component
public final class EmailService {

}
```

This is allowed.

Why?

Because Spring does not need to subclass every component.

It can simply do:

```text
new EmailService()
```

and manage it.

---

## `@Configuration`

Example:

```java
@Configuration
public final class AppConfig {

}
```

Not allowed.

Because Spring needs:

```text
AppConfig
     ↓
CGLIB Proxy
     ↓
override @Bean methods
```

# 7. What happens if you disable proxying?

Spring has a mode:

```java
@Configuration(proxyBeanMethods = false)
```

Example:

```java
@Configuration(proxyBeanMethods = false)
public final class AppConfig {


    @Bean
    public UserService userService(){

        return new UserService();
    }

}
```

This can work because Spring does not create a CGLIB proxy.

The behavior changes.

---

# 8. `proxyBeanMethods` explanation

Default:

```java
@Configuration
public class AppConfig {

}
```

means:

```java
@Configuration(proxyBeanMethods = true)
```

Spring creates proxy.

---

With:

```java
@Configuration(proxyBeanMethods = false)
```

Spring uses a simpler mode:

```text
No CGLIB proxy
No method interception
```

Each `@Bean` method behaves more like a normal Java method.

---

# 9. Example difference

## Normal configuration

```java
@Configuration
public class Config {


    @Bean
    public A a(){

        return new A();
    }


    @Bean
    public B b(){

        return new B(a());
    }
}
```

Spring proxy ensures:

```text
b()
 |
 ↓
same A Bean
```

---

## `proxyBeanMethods=false`

```java
@Configuration(proxyBeanMethods=false)
public class Config {


    @Bean
    public A a(){

        return new A();
    }


    @Bean
    public B b(){

        return new B(a());
    }
}
```

Now:

```text
b()
 |
 ↓
call a()

 |
 ↓
new A()
```

Potentially:

```text
A instance #1

A instance #2
```

unless Spring injects the dependency differently.

# 10. Why did Spring choose CGLIB?

Spring originally used:

* JDK Dynamic Proxy → requires interfaces
* CGLIB → subclassing classes

`@Configuration` classes usually do not implement interfaces:

```java
@Configuration
public class AppConfig {

}
```

Therefore:

```text
JDK Proxy ❌

CGLIB Proxy ✅
```

# 12. Exam-ready answer

Question:

> **Why are you not allowed to annotate a final class with `@Configuration`?**

A strong answer:

> **A `@Configuration` class is enhanced by Spring using a CGLIB proxy. Spring creates a subclass of the configuration class to intercept calls to `@Bean` methods and ensure that singleton Beans are returned from the ApplicationContext instead of creating new instances. Since a `final` class cannot be subclassed, Spring cannot create the required proxy, so a final class cannot be used as a standard `@Configuration` class.**

---

# What is the `Environment` abstraction in Spring?

The **`Environment`** abstraction in Spring represents the application's **runtime environment and configuration**.

In simple terms:

> **`Environment` is Spring's central interface for accessing configuration properties and determining which profiles are active.**

It connects directly to the topics we've just studied:

```text
Property Sources
      ↓
Environment
      ↓
 ┌────┴────┐
 ↓         ↓
Properties Profiles
 ↓         ↓
@Value    @Profile
```

---

# 1. Why does Spring need `Environment`?

Imagine your application needs:

```text
database.url
database.username
server.port
app.name
app.timeout
```

These values could come from many different places:

```text
application.properties
application.yml
environment variables
JVM system properties
command-line arguments
custom property files
```

You don't want every Bean to know where the value came from.

Instead, Spring provides a common abstraction:

```text
                  Spring
                    │
             Environment
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
 properties    environment    system
   files         variables    properties
```

Your application simply asks:

```java
environment.getProperty("app.name");
```

Spring handles the underlying property sources.

---

# 2. `Environment` is an interface

The important type is:

```java
org.springframework.core.env.Environment
```

For example:

```java
@Component
public class AppInfo {

    private final Environment environment;

    public AppInfo(Environment environment) {
        this.environment = environment;
    }

    public void print() {
        String name =
            environment.getProperty("app.name");

        System.out.println(name);
    }
}
```

Spring automatically injects the `Environment` object.

So:

```text
ApplicationContext
       │
       ├── Beans
       │
       └── Environment
              │
              ├── Properties
              └── Active Profiles
```

---

# 3. `Environment` has two major responsibilities

This is the key point for an exam.

`Environment` primarily provides:

### ① Property access

```java
environment.getProperty("app.name");
```

### ② Profile information

```java
environment.getActiveProfiles();
```

So remember:

```text
Environment
   │
   ├── Properties
   │
   └── Profiles
```

---

# 4. Reading properties

Suppose you have:

```properties
app.name=Order System
app.port=8080
app.enabled=true
```

You can access them:

```java
@Component
public class AppInfo {

    private final Environment environment;

    public AppInfo(Environment environment) {
        this.environment = environment;
    }

    public void print() {

        String name =
            environment.getProperty("app.name");

        Integer port =
            environment.getProperty(
                "app.port", Integer.class);

        Boolean enabled =
            environment.getProperty(
                "app.enabled", Boolean.class);

        System.out.println(name);
        System.out.println(port);
        System.out.println(enabled);
    }
}
```

Output:

```text
Order System
8080
true
```

Notice that Spring can perform **type conversion**.

---

# 5. Providing a default value

You can also specify a default:

```java
String name =
    environment.getProperty(
        "app.name",
        "Default Application"
    );
```

If `app.name` doesn't exist:

```text
app.name exists?
      │
   ┌──┴──┐
  yes    no
   │      │
   ↓      ↓
 value   default
```

---

# 6. Type conversion

You can ask Spring for a specific type:

```java
Integer port =
    environment.getProperty(
        "server.port",
        Integer.class
    );
```

Instead of:

```java
String port =
    environment.getProperty("server.port");

int value =
    Integer.parseInt(port);
```

Spring's conversion system can perform the conversion for you.

---

# 7. Checking whether a property exists

You can use:

```java
if (environment.containsProperty("app.name")) {
    System.out.println("app.name exists");
}
```

This is useful when configuration is optional.

---

# 8. `Environment` and Spring Profiles

The second major purpose of `Environment` is **profiles**.

Suppose:

```properties
spring.profiles.active=dev
```

You can ask:

```java
String[] profiles =
    environment.getActiveProfiles();
```

You might get:

```text
["dev"]
```

You can also check:

```java
boolean dev =
    environment.matchesProfiles("dev");
```

Conceptually:

```text
Environment
     │
     ├── Properties
     │
     │    app.name
     │    server.port
     │    database.url
     │
     └── Profiles
          │
          ├── dev
          ├── test
          └── prod
```

This is why `Environment` is closely related to the `@Profile` topic you just learned.

---

# 9. `Environment` vs Property Source

These two concepts are easy to confuse.

### Property Source

A **PropertySource** is one particular source of configuration.

For example:

```text
application.properties
```

could be one property source.

Another could be:

```text
Environment variables
```

Another:

```text
System properties
```

### Environment

`Environment` is the abstraction that **organizes/accesses these property sources and profiles**.

Think:

```text
PropertySource 1
      │
PropertySource 2
      │
PropertySource 3
      │
      ↓
 Environment
      │
      ↓
getProperty(...)
```

So:

> **PropertySource = where a property comes from.**

> **Environment = Spring's abstraction for accessing configuration and profiles across those sources.**

---

# 10. `Environment` vs `ApplicationContext`

This distinction is also important.

`ApplicationContext` is Spring's **IoC container**.

It manages:

```text
Beans
Dependencies
Lifecycle
Events
Resources
Environment
...
```

`Environment` focuses primarily on:

```text
Properties
Profiles
```

So:

```text
ApplicationContext
       │
       ├── Bean management
       │
       ├── Dependency Injection
       │
       ├── Lifecycle
       │
       ├── Events
       │
       └── Environment
              │
              ├── Properties
              └── Profiles
```

In fact, `ApplicationContext` provides access to its environment:

```java
Environment environment =
    context.getEnvironment();
```

# 11. `Environment` vs `@Value`

You can access the same configuration in different ways.

### Using `@Value`

```java
@Value("${app.name}")
private String name;
```

### Using `Environment`

```java
private final Environment environment;

public MyService(Environment environment) {
    this.environment = environment;
}

String name =
    environment.getProperty("app.name");
```

Conceptually:

```text
                 Environment
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       @Value              getProperty()
          ↓                     ↓
        Bean              Java code
```

### When to use which?

For simple static configuration:

```java
@Value("${app.name}")
```

is convenient.

If you need to **programmatically query configuration**, `Environment` is useful:

```java
if (environment.containsProperty("feature.x")) {
    ...
}
```

---

# 12. `Environment` and `@ConfigurationProperties`

There's another approach you've just learned:

```java
@ConfigurationProperties(prefix = "app")
```

For example:

```java
@ConfigurationProperties(prefix = "app")
public class AppProperties {

    private String name;
    private int port;
    private boolean enabled;

    // getters/setters
}
```

So we have three related mechanisms:

```text
Configuration
     │
     ↓
Environment
     │
     ├──────────────┐
     ↓              ↓
   @Value    @ConfigurationProperties
```

The important difference is:

```text
Environment
    ↓
low-level/general access to properties

@Value
    ↓
inject individual values

@ConfigurationProperties
    ↓
bind a group of related properties
```

# 13. A practical example

Suppose:

```properties
app.name=Order System
app.timeout=5000
spring.profiles.active=dev
```

A Bean can access everything through `Environment`:

```java
@Component
public class AppInfo {

    private final Environment environment;

    public AppInfo(Environment environment) {
        this.environment = environment;
    }

    public void printInfo() {

        String name =
            environment.getProperty("app.name");

        Integer timeout =
            environment.getProperty(
                "app.timeout",
                Integer.class
            );

        String[] profiles =
            environment.getActiveProfiles();

        System.out.println("Name: " + name);
        System.out.println("Timeout: " + timeout);
        System.out.println(
            "Profiles: " +
            String.join(", ", profiles)
        );
    }
}
```

Output might be:

```text
Name: Order System
Timeout: 5000
Profiles: dev
```

# 14. The conceptual chain

This is probably the most useful way to remember the topic.

```text
                 Configuration
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
     properties    env variables   system props
          │            │            │
          └────────────┼────────────┘
                       ↓
                Property Sources
                       │
                       ↓
                  Environment
                   /        \
                  /          \
                 ↓            ↓
            Properties      Profiles
                 │            │
             getProperty()   getActiveProfiles()
                 │            │
                 ↓            ↓
               Beans        @Profile
```

And the bigger Spring picture:

```text
Java Objects
     ↓
Dependency Injection
     ↓
IoC Container
     ↓
ApplicationContext
     │
     ├── Bean management
     │
     └── Environment
            │
            ├── Property Sources
            ├── Properties
            └── Profiles
```

## Exam-ready answer

> **The `Environment` abstraction in Spring represents the environment in which an application is running. It provides access to configuration properties from various property sources and provides information about active and default profiles. It can be accessed through `ApplicationContext` or injected directly into a Bean.**

### Short version to memorize

```text
Environment = Spring's configuration + profile abstraction

Main responsibilities:
    1. Access properties
       environment.getProperty("app.name")

    2. Access profiles
       environment.getActiveProfiles()

PropertySource → individual configuration source
Environment    → abstraction over properties + profiles
ApplicationContext → IoC container that also provides Environment
```

So the conceptual chain you've learned is now:

**Property Source → `Environment` → `@Value` / `@ConfigurationProperties` / `@Profile` → Spring Beans.**

An invariant is a mathematical or logical condition that must always remain true at a specific point in your code, no matter what operations the program performs. If an invariant evaluates to false, it means the application's internal structure has been corrupted due to a core developer bug.

In Java, you test these fundamental system rules by using assertions (assert). They act as structural checkpoints to enforce internal contracts.

------------------------------
## 1. Types of Invariants Tested by Assertions
When debugging Java applications, you will typically validate three forms of invariants:

* Internal Invariants: Assuring a specific constraint holds true for a local variable (e.g., verifying a computed score is never negative).
* Control-Flow Invariants: Enforcing that an unreachable area of code is never hit (e.g., the default block of a switch statement covering an enum).
* Class Invariants: Verifying that an object's overall state remains completely valid before and after a private modification.

------------------------------
## 2. Implementation: Testing an Internal Invariant
You use the assert keyword followed by a boolean condition. You can optionally append a colon (:) and an error message string to supply details if the validation fails.

public class PhysicsEngine {
    private double currentSpeed = 0.0;
    private static final double SPEED_OF_LIGHT = 299792458.0; // m/s

    private void accelerateParticle(double energyInput) {
        // ... complex internal math calculations ...
        this.currentSpeed += (energyInput * 0.05);

        // INVARIANT CHECK: It is physically impossible to exceed light speed.
        // If this is false, the formula itself has a bug.
        assert currentSpeed < SPEED_OF_LIGHT : "Logic Error: Speed exceeded light speed! " + currentSpeed;
    }
}

If the invariant condition evaluates to false, the Java Virtual Machine (JVM) immediately throws an AssertionError and halts the application to prevent data corruption.

------------------------------
## 3. Implementation: Testing a Control-Flow Invariant
If you code a path that you assume can never execute under any circumstances, place assert false; at that exact position.

public class CardDealer {
    enum Suit { CLUBS, DIAMONDS, HEARTS, SPADES }

    public void processSuit(Suit suit) {
        switch (suit) {
            case CLUBS:    /* Logic */ break;
            case DIAMONDS: /* Logic */ break;
            case HEARTS:   /* Logic */ break;
            case SPADES:   /* Logic */ break;
            default:
                // CONTROL-FLOW INVARIANT: All enum variants are handled.
                // Execution should never reach this point.
                assert false : "Unknown card suit encountered: " + suit;
        }
    }
}

------------------------------
## 4. Rule of Thumb: When to use Exceptions vs. Assertions
A common design mistake is replacing proper runtime input validation with assertions. Use this breakdown to differentiate them:

| Scenario | Use Exceptions (throw / catch) | Use Assertions (assert) |
|---|---|---|
| Validation Target | Public method arguments, user input, external network/file configurations. | Private method internal parameters, logic results, structural loop states. |
| Environment | Production & Live Systems (Must catch errors and keep running). | Development & Testing (Used to flush out logic bugs quickly). |
| JVM Execution | Always active. | Disabled by default; must be explicitly enabled via the -ea flag. |

Note: Because assertions are stripped out or ignored in production code for optimization purposes, you must never write state-changing application logic inside an assertion statement (e.g., assert modifyBalance() > 0;), otherwise that code will not execute when deployed.

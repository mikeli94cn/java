In Java, every class you create automatically inherits from a master parent class: java.io.Object (or more simply, the Object class). 

This universal parent provides a set of foundational methods—specifically toString(), equals(), and hashCode()—that dictate how your custom objects are printed, compared, and managed inside collections.

However, the default implementations provided by the Object class are highly generic and usually inadequate for real-world classes. 

To make your custom classes behave predictably, you must override these three methods to work with your object's actual data.


## 1. The toString() Method (Textual Representation)

* Default Behavior: Prints the class name followed by an @ symbol and the object's hexadecimal memory address (e.g., `User@1a2b3c4d`).
* Why Override It? To provide a clean, human-readable summary of the object's internal data—making logging, console printing, and debugging significantly easier.
```java
public class User {
    private String username;
    private int id;

    public User(int id, String username) {
        this.id = id;
        this.username = username;
    }

    // Overriding toString to display meaningful data fields
    @Override
    public String toString() {
        return "User[ID=" + id + ", Name='" + username + "']";
    }
}
```

* The Result: Calling `System.out.println(myUser)` will now print `User[ID=101, Name='Alex']` instead of cryptic memory addresses.


## 2. The equals(Object obj) Method (Data Identity)

* Default Behavior: Compares objects using the == operator, meaning it returns true only if both variables point to the exact same memory location on the heap.
* Why Override It? To enforce logical equality. For example, if two separate User objects have the exact same id number, business logic usually dictates that they represent the same person, regardless of where they live in memory.
```java
@Overridepublic boolean equals(Object obj) {
    if (this == obj) return true; // Step 1: Memory check
    if (obj == null || getClass() != obj.getClass()) return false; // Step 2: Null/Type check
    
    User otherUser = (User) obj; // Step 3: Cast to target type
    return this.id == otherUser.id; // Step 4: Compare logical identifying fields
}
```

## 3. The hashCode() Method (Collection Indexing)

* Default Behavior: Generates an integer value based entirely on the unique memory address of the object instance.
* Why Override It? If your object is stored inside hash-based collections (like HashMap or HashSet), Java uses this integer code as a bucket coordinate to store and find your data instantly.

## The Golden Rule of Java Objects: The Equals-HashCode Contract

If two objects are equal according to the .equals() method, they must return the exact same integer value from their .hashCode() method.

If you violate this contract (by overriding equals but forgetting to override hashCode), your objects will get lost or duplicated inside HashMap structures, causing massive application bugs.
```java
import java.util.Objects;

@Overridepublic int hashCode() {
    // Generates a hash based on the exact same fields used in the equals method
    return Objects.hash(id); 
}
```

## Summary Checklist for Object Methods

| Method Signature | Default Object Behavior | Overridden Goal | Collection Impact |
|---|---|---|---|
| public String toString() | ClassName@MemoryAddress | Returns a clean, readable text summary of the fields. | Used automatically by System.out.println() and string concatenation. |
| public boolean equals(Object o) | Compares memory addresses (==). | Compares data values inside fields. | Essential for lookup operations like list.contains(). |
| public int hashCode() | Memory address integer translation. | Generates a shared numeric fingerprint matching equals rules. | Required for objects to function as keys inside a HashMap or HashSet. |

In Java class design, encapsulation is the foundational practice of bundling data (fields) and behaviors (methods) into a single blueprint while restricting direct access to the object's internal state []. It is the technical implementation of "data hiding."
Think of a modern smartphone: you interact with the clean, external screen and buttons (the public interface), while the complex wiring and battery are sealed safely inside (the private state). This prevents you from accidentally short-circuiting the device while using it.

------------------------------
## The 3 Structural Requirements of Encapsulation
To implement proper encapsulation in a Java class, you must follow a strict three-step design pattern:

1. Private Fields ──────────> Hide the raw data variables from external classes.
2. Public Getter Methods ───> Provide secure, controlled read-only access.
3. Public Setter Methods ───> Provide secure, validated write-only modifications.

------------------------------
## Code Blueprint: An Encapsulated Employee Class
Here is how to build a production-ready, encapsulated class. Notice how the setter method filters out invalid inputs before they can corrupt the object's internal data:

public class Employee {
    // Step 1: Mark all instance fields as private
    private String name;
    private double salary;

    // Constructor to initialize data at creation
    public Employee(String name, double salary) {
        this.name = name;
        setSalary(salary); // Routes through the setter to enforce data validation rules immediately
    }

    // Step 2: Public Getter for Name (Read Access)
    public String getName() {
        return this.name;
    }

    // Step 2: Public Getter for Salary (Read Access)
    public double getSalary() {
        return this.salary;
    }

    // Step 3: Public Setter for Salary (Controlled Write Access with Business Logic)
    public void setSalary(double salary) {
        if (salary >= 0) {
            this.salary = salary; // 'this' distinguishes the class field from the local argument
        } else {
            System.out.println("Error: Salary cannot be a negative value!");
        }
    }
}

------------------------------
## Utilizing the Encapsulated Class
By wrapping the fields in methods, external code can no longer accidentally insert broken or corrupt data into our objects:

public class Main {
    public static void main(String[] args) {
        Employee emp = new Employee("Sarah", 75000.00);

        // ❌ COMPILER ERROR: Direct access is completely blocked!
        // emp.salary = -500.00; 

        //  CORRECT: Updates route safely through the validated setter
        emp.setSalary(80000.00); // Successfully updated
        emp.setSalary(-1200.00); // Blocks execution and prints the error message

        //  CORRECT: Reading data via the getter
        System.out.println(emp.getName() + " earns $" + emp.getSalary());
    }
}

------------------------------
## Strategic Advantages of Encapsulation

* Enforced Data Integrity: Setters act as gatekeepers, validating inputs (like ensuring ages aren't negative or emails contain an @ symbol) before saving them.
* Class Flexibility (Maintainability): If you decide to change how salary is stored (e.g., changing from a double to a BigDecimal), you only modify the code inside the Employee class. All external classes calling getSalary() remain completely unbroken.
* Read-Only or Write-Only Access: By simply omitting a setter method, you instantly make a field read-only to the rest of your application.

------------------------------
## Summary Architectural Matrix

| Component | Visibility Modifier | Primary Role | Analogy |
|---|---|---|---|
| Variables/Fields | private | Restricts external exposure; holds raw state. | A locked business safe. |
| Getters (get...) | public | Safely returns a copy of a field's value. | Viewing a receipt. |
| Setters (set...) | public | Validates, filters, and records data modifications. | Making a deposit through a bank teller. |
